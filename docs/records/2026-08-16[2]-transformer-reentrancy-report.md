# Реентерабельность трансформеров логов (0.5.1)

## Откуда взялось

Пункт бэклога, пришедший из финального ревью 0.5.0: «логирование через
тот же логгер из transformer'а рекурсирует до StackOverflowError;
fail-closed выдерживает, но публикуется лавина повторов». Требовалось
предупреждение в dartdoc, опционально — guard.

## Что показал замер

Формулировку проверил, а не принял на веру. Один вызов `log.i(...)`
с трансформером, логирующим в тот же логгер:

| Сценарий | Опубликовано | Ошибок в зону |
|---|---|---|
| `CustomLogger.transformer` | ~2700 | 1 × `StackOverflowError` |
| `TransformPublisher` | ~2000 | 1 × `StackOverflowError` |

`StackOverflowError` ловится fail-closed-обработчиком на дне рекурсии,
но каждый разматывающийся кадр после этого спокойно доходит до
`_publisher.publish(...)` — отсюда тысячи дублей.

**Важнее:** «fail-closed выдерживает» оказалось не гарантией, а
везением. Под `runZonedGuarded` с цепочкой зон (например, внутри
`dart test`) сам обработчик падает:

```
Unhandled exception:
Stack Overflow
#0  _Zone._processUncaughtError (dart:async/zone.dart:552:3)
#4  _CustomZone.handleUncaughtError
#5  CustomLevelLogger.publishLog (custom_level_logger.dart:141:22)
```

`Zone.current.handleUncaughtError` в `catch` сам требует стека, которого
уже нет, и `StackOverflowError` из него уходит необработанным — изолят
падает. Первая формулировка dartdoc («the isolate survives»), написанная
до этого замера, была неверной и переписана.

## Решение

Флаг на экземпляре, взводимый только вокруг вызова трансформера:
`CustomLogger._transforming` и `TransformPublisher._transforming`.
Реентерабельный вызов детектируется, вложенный лог отбрасывается,
в `onError` или в зону уходит `StateError`.

Три детали:

- Флаг снимается **до** передачи лога паблишеру. Иначе цепочка
  «трансформер логгера → `MultiPublisher` → `TransformPublisher`»
  считалась бы реентерабельной.
- Guard на экземпляре, а не статический на библиотеку. Статический ловил
  бы и циклы, но запрещал бы законный случай — логирование из
  трансформера в посторонний аудит-логгер со своим трансформером.
- Покрытие оказалось шире ожидаемого: ловится **любой** цикл, который
  возвращается к логгеру, чей трансформер уже выполняется, в том числе
  через несколько логгеров (A→B→A проверено тестом). Не ловится только
  бесконечная цепочка всё новых экземпляров логгера.

Цены для тех, у кого `transformer == null` (значение по умолчанию), нет:
проверка живёт внутри ветки, которая и так выполняется только при
заданном трансформере.

## Вторая находка: README и примеры обходили трансформер

Пока копал, обнаружил, что breaking-изменение 0.5.0 («`processLog`
обязан звать `publishLog`, а не `publisher.publish`») задокументировали
в CHANGELOG, но не применили к самим материалам: все четыре логгера
в `example/logger_builder_examples/lib/` и два фрагмента README
показывали старую форму. То есть у любого, кто начинал с примера,
`CustomLogger.transformer` — главная фича 0.5.0 — молча не работал.

Мигрировал README, четыре примера и тестовую фикстуру
`test/utils/variable_logger.dart`; в README добавил объяснение, зачем
именно `publishLog`. Проверено прогоном: с `transformer = (l) => null`
логгер из примера теперь ничего не публикует, до правки публиковал.

## Тесты

`test/transformer_test.dart` — новая группа `CustomLogger.transformer
reentrancy` (6 тестов): вызов через тот же логгер, вызов на другом
уровне того же логгера, работоспособность после срабатывания, отсутствие
ложного срабатывания на постороннем логгере, цикл из двух логгеров,

с `TransformPublisher`.

`test/transform_publisher_test.dart` — реентерабельный трансформер
и цепочка из двух `TransformPublisher` без ложного срабатывания.

Итого 136 → 145 тестов.

## Замечание о красной фазе

Тест «a nested call on another level of the same logger is caught»
в красной фазе не падал, а ронял изолят, из-за чего `dart test` вис без
вывода. Это и вывело на находку про `handleUncaughtError`. Если понадобится
воспроизвести — запускать с записью вывода в файл и внешним сторожевым
таймером, иначе картина теряется.
