# Три утверждения README: что оказалось правдой

Три пункта бэклога, все одного жанра: README что-то утверждает, и никто
этого не мерил. Ниже — чем каждое кончилось.

Пункты из `docs/backlog.md` убраны, но в истории git этого не видно:
владелец дописал их в рабочее дерево, не коммитя, поэтому удаление
вернуло файл к тому, что и так лежит в `HEAD`, — диффа нет. Поэтому все
три утверждения процитированы ниже дословно: кроме этой записи, их текста
больше нигде нет.

## Как мерилось

Первые два пункта — измерением, третий — компиляцией.

Для измерений в `example/logger_builder_examples/bin/benchmarks.dart`
добавлены три секции: «Cheap payload, three ways» при включённом и при
выключенном уровне и «processLog: closure vs method». Методика — та же,
что у остальных секций файла (`runTest`): 1 млн вызовов, прогрев, десять
повторов, среднее по лучшей половине. Файл исключён из шага CI «Run the
examples» по имени, так что новые секции время сборки не удлиняют.

Для пункта про `processLog` в файл добавлены две пары классов
(`ClosureLogger`/`ClosureLevelLogger` и `MethodLogger`/`MethodLevelLogger`),
различающиеся **ровно одной строкой** — тем, как отдаётся `processLog`.
Нагрузка нарочно вырожденная: `MicroLog` с единственным полем, паблишер
только паркует сообщение в глобальную переменную. Переменная в конце
прогона читается — иначе запись, которую никто не читает, компилятор
вправе выбросить, и мерились бы два пустых цикла.

Три прогона AOT (`dart compile exe`) и один JIT (`dart run`), Dart 3.13.0,
macOS. Разброс между прогонами AOT — единицы процентов, картина во всех
трёх одна.

## Пункт 1: `processLog` замыканием против метода

Утверждение README: «Theoretically, the second option should be more
performant, as it does not create a `closure` on each call. But in practice,
the compiler makes the difference minimal».

**Вывод верен, обоснование — нет, и неверна именно та часть, ради которой
абзац написан.** Замыкание не создаётся на каждом вызове. `processLog`
читается ровно один раз на переключение уровня:
`_log = enabled ? processLog : _noLog` в
`lib/src/custom_logger/custom_level_logger.dart:339`. Комментарием двумя
строками выше это уже зафиксировано в коде («`processLog` allocates a fresh
closure in every documented pattern») — как цена включения уровня, а не
вызова. Дальше оба варианта одинаковы: вызов через объект-функцию в поле
`_log`, будь то замыкание, захватившее `this`, или bound tear-off метода,
созданный тогда же однажды.

Измерения (нс на вызов, включённый уровень):

| Форма | AOT (3 прогона) | JIT |
|---|---|---|
| `=> (message, {...}) { ... }` | 10.39 / 10.24 / 10.67 | 11.91 |
| `=> _processLog` | 11.94 / 11.69 / 12.30 | 11.69 |

Разница меньше 2 нс, и знак её не устойчив: в AOT впереди замыкание, в JIT
— метод. То есть «на практике разница минимальна» подтвердилось, а «метод
теоретически быстрее, потому что не создаёт замыкание на каждом вызове» —
опровергнуто дважды: и как механика, и как направление.

В README абзац переписан: оба варианта равноценны, `processLog` читается
раз на включение уровня, числа приведены с указанием обоих компиляторов,
выбор — по читаемости.

## Пункт 2: «замыкания во всех случаях»

Утверждение README: «I recommend using closures in all cases when you pass
something other than ready-made values, even if it's a simple string with
minor interpolations or something like `i++`. Better safe than sorry».

**Подтвердилось, и в бенчмарке нашлась дыра, из-за которой проверить это
раньше было нечем.** Ленивый случай в `benchmarks.dart` был написан как
`log.i(evaluateMessage)` — тер-офф уже существующей функции, который на
вызов не аллоцирует ничего. А README рекомендует `log.d(() => ...)` —
литерал замыкания с захватом, по объекту на каждый вызов. Мерилась форма
выгоднее той, которую советуют. Теперь в файле рядом стоят все три.

Измерения (нс на вызов, AOT, первый прогон; JIT в скобках):

| Форма | уровень включён | уровень выключен |
|---|---|---|
| `log.i('... #${++counter}')` | 134.30 (122.47) | 41.42 (36.64) |
| `log.i(evaluateMessage)` | 135.97 (125.03) | 1.92 (2.68) |
| `log.i(() => '... #${++counter}')` | 138.32 (125.96) | 3.61 (5.07) |

Асимметрия и есть ответ. При включённом уровне замыкание стоит около 3 нс
поверх ~135 нс, которые тратятся всё равно, — 2–3%, погрешность. При
выключенном оно превращает 41 нс в 4 нс — порядок величины. Проигрыш
пренебрежим, выигрыш огромен, значит рекомендация «во всех случаях»
оправданна, и теперь у неё есть числа вместо «better safe than sorry».

Заодно видно цену самого литерала против тер-оффа: 3.6 нс против 1.9 нс на
выключенном уровне — это и есть аллокация на вызов. Обе формы на порядок
дешевле жадной сборки строки, так что разница между ними на выбор не
влияет, но в README она названа: рекомендация теперь говорит и про то,
когда лишней аллокации можно избежать.

## Пункт 3: «`print` always writes to stdout» на web

**Не подтвердилось для web, и рядом нашлось кое-что хуже самого
утверждения.**

Что делает `print`, видно прямо в выводе компилятора. `dart compile js`
порождает `printString`: сначала `dartPrint`, если встраивающий код такую
функцию определил, затем `console.log`, затем глобальный `print`, иначе
`throw "Unable to print message"`. `dart compile wasm` порождает
`printToConsole` с той же цепочкой. Никакого stdout в ней нет.

Дальше начинается разница между хостами. Под Node `console.log` уходит
в stdout, а `console.error` — в stderr (проверено запуском). В браузере
это консоль devtools. Но `console.error` Dart не вызывает никогда, поэтому
на web рецепт из раздела «How to log to stdout and stderr» не просто
неточен — он неисполним: разделять там нечего.

Хуже другое, и в бэклоге этого не было. Сам рецепт опирается на `dart:io`,
и на web он **компилируется**: `dart compile js` с `import 'dart:io'`
собирается молча (96 КБ выходного js). Падает он в рантайме —
`Unsupported operation: StdIOUtils._getStdioOutputStream`. То есть
пользователь, скопировавший рецепт во flutter-web или в js-сборку,
получает не ошибку сборки, а падение у пользователя.

В README фраза сужена до нативных платформ, а после блока кода добавлена
врезка `> [!NOTE]` про web: куда на самом деле идёт `print` в js и wasm,
что `dart:io` компилируется и бросает в рантайме, и что развести stdout
и stderr на web этим способом нельзя вовсе.
