# Дефолтный `onDropped`: пакет говорит сам

## Задача

Граница очереди закрыла `M10` только для тех, кто задал `onDropped`. Кто
не задал — теряет логи так же молча, как раньше, и это ровно те, кто
документацию не читал. Предложение владельца: дать `onDropped`
реализацию по умолчанию, сообщающую о пропусках с debounce в несколько
секунд.

## Решения и почему

**Печатать, а не отдавать в зону.** Симметрия с `onError` (у него дефолт
— `Zone.current.handleUncaughtError`) здесь ловушка: в обычной
Dart-программе без error-зоны непойманная асинхронная ошибка завершает
изолят. `onError` срабатывает, когда хендлер бросил, — редко и по ошибке
в коде. Потери идут пачками и ровно под нагрузкой, и убивать приложение
за то, что оно не успевает писать логи, — худший из возможных ответов.

Это делает пакет говорящим впервые: сегодня в `lib/` нет ни одного
`print`. Цена принята сознательно — молчаливая потеря хуже строки
в консоли, а заглушить её можно одним `onDropped: (_) {}`.

**Без таймеров.** Окно проверяется по часам в момент самого
отбрасывания: первый лог, перешагнувший границу окна, печатает строку.
Взведённый таймер точнее, но он живой корень для цикла событий — пакет
уже ловил этим воркер, который не мог выйти из `main` (дартдок
`maxRetries` про это прямо говорит). Продлевать жизнь процесса на пять
секунд из-за отброшенного лога — плохой обмен.

**Первая потеря печатается сразу.** Иначе короткая программа, уронившая
сто логов и завершившаяся, не скажет ничего. Дальше окно молчит
и печатает итог; итог допечатывается и на `close()`, иначе последняя
пачка останется несосчитанной.

**Окно 5 с с удвоением до минуты.** 5, 10, 20, 40, 60 — и потолок. Тот
же приём, что у `retryDelay`. Часовая авария даёт порядка пятнадцати
строк вместо семисот. Если между потерями прошло больше двух окон, шторм
считается кончившимся и окно сбрасывается к пяти секундам.

## Устройство

Новый внутренний файл `internal/dropped_reporter.dart`, класс
`DroppedReporter`. Публичная поверхность пакета не растёт **ни на один
член**: меняется только то, что значит `onDropped == null`.

```dart
enum DropCause { queueFull, retriesSpent, closed }

final class DroppedReporter {
  DroppedReporter({
    this.window = const Duration(seconds: 5),
    this.cap = const Duration(minutes: 1),
    this.sink = print,
  });
  void record(int count, DropCause cause);
  void flush();
}
```

`window`, `cap` и `sink` — параметры с умолчаниями, а не константы: это
шов для тестов, а не настройка. Наружу они не выходят, потому что файл
лежит в `internal/` и barrel'ом не экспортируется.

Алгоритм `record`:

1. прибавить счёт к накопленному, запомнить причину;
2. первая потеря за жизнь репортёра — напечатать сразу и завести
   секундомер;
3. иначе, если с прошлой печати прошло не меньше окна, — напечатать
   итог, обнулить счёт, перезапустить секундомер и удвоить окно
   с потолком; если прошло больше двух окон, вернуть окно к базовому.

`flush` печатает остаток, если он есть, и ничего не делает иначе.

Репортёр создаётся лениво, на первой потере при пустом `onDropped`, —
в обычной жизни его нет вовсе.

### Проводка

`AsyncPipeline._reportDropped(E entry)`: колбэк задан — как сейчас, под
`guarded`; не задан — `_reporter.record(1, DropCause.queueFull)` (у этой
пары других причин нет).

`BufferedPipeline._reportDropped` получает причину: переполнение —
`queueFull`, исчерпанный бюджет — `retriesSpent`, закрытие — `closed`.
Колбэк задан — как сейчас; не задан — в репортёр.

`flush()` репортёра зовётся из `_close()` обоих движков **после**
дренажа: потери при закрытии происходят во время него.

### Текст

По-английски, как все тексты ошибок (`AGENTS.md` §6). Первая строка
и итоговая строятся одинаково:

```
logger_builder: 12483 log events dropped in the last 5.0s (queue full).
Set onDropped to handle them, or onDropped: (_) {} to silence this.
```

Причин в окне может быть несколько — перечисляются через запятую.

## Что меняется для пользователя

`onDropped == null` больше не значит «тишина». Это изменение поведения
и идёт в `CHANGELOG.md` под `[breaking changes]`: приложение, которое
теряло логи молча, начнёт писать об этом в консоль. Заглушается пустым
колбэком.

Дартдок `onDropped` на четырёх базах сегодня говорит «без этого колбэка
потеря не оставляет следа» — это станет неправдой и правится тем же
коммитом, вместе с обоими README.

## Чего в этой работе нет

- Настройки окна снаружи: кому нужно иначе — задаёт свой `onDropped`.
- Счётчика-геттера: он обсуждался и отклонён вместе с формой `onDropped`.
- Форматирования потерянных логов: репортёр печатает счёт, а не записи.
  Спасать сами логи — работа пользовательского колбэка.

## План работ

1. `internal/dropped_reporter.dart` + прямые тесты на репортёр (окно,
   удвоение, сброс, `flush`) через шов `sink` и короткое окно.
2. Проводка в `AsyncPipeline` и тесты через публичный API: первая потеря
   печатается, вторая в окне — нет, заданный `onDropped` печать
   отменяет, `close()` допечатывает итог.
3. То же для `BufferedPipeline`, включая три причины.
4. Документы: дартдок четырёх баз, оба README, `CHANGELOG.md`,
   `docs/architecture.md`.
5. Проверки чеклиста §7 целиком, отчёт, `docs/handoff.md`.
